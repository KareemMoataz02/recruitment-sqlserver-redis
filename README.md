# RecruitmentDb: SQL Server + Redis

A runnable recruitment API with Redis cache-aside caching, an interactive browser lab, atomic SQL workflows, and integration tests against real SQL Server and Redis instances.

## What is included

- Final Jadarat database: 13 related tables, constraints, indexes, status-history triggers, a current-status view, and realistic fictional sample records.
- Scalar application-count function, validated status-history procedure, and transactional application + skill procedure.
- Cached applicant-count endpoint, 60-second expiry, post-commit invalidation, and SQL fallback when Redis is unavailable.
- Browser lab showing `MISS`, `HIT`, `BYPASS`, response time, and SQL count-query totals.
- Twelve integration tests, isolated test resources, and GitHub Actions CI.
- [Full project specification](docs/SPECIFICATION.md), [OpenAPI contract](docs/openapi.yaml), [test guide](docs/TESTING.md), editable diagrams, and submission PDFs.

## Requirements

An x86-64 host supported by the SQL Server Linux image, Node.js 22 or later, npm, and Docker Compose or Podman with a Compose provider. Allocate at least 4 GB to SQL Server. SQL Server Developer edition is used for development/testing.

The defaults use ports **3102** (API), **1434** (SQL Server), and **6380** (Redis), so this clone can run alongside the earlier local lab.

## Fresh-clone setup

```bash
git clone https://github.com/KareemMoataz02/recruitment-sqlserver-redis.git
cd recruitment-sqlserver-redis
./scripts/init-env.sh
npm ci
```

`init-env.sh` creates a mode-600 `.env` file with a random password. It never overwrites an existing file. Do not commit `.env`.

Choose one container engine:

```bash
# Docker
# Set CONTAINER_ENGINE=docker in .env before running npm test.
docker compose up -d --wait

# Or Podman (requires a Compose provider)
podman compose up -d --wait
```

Then create the database, install SQL workflows, and start the API:

```bash
npm run setup
npm start
```

Open **http://127.0.0.1:3102/**. Click **Clear this cache**, then **Read twice** to observe **MISS → HIT**. The first request runs the SQL count function; the second uses Redis. After 60 seconds, the next request misses again.

`npm run setup` seeds only when RecruitmentDb is absent. It preserves an existing database and reinstalls the function/procedures. If the existing database lacks the expected final schema, setup stops rather than resetting it.

## Test

```bash
npm run check
npm test
```

Tests create a uniquely named disposable database and Redis container, exercise real HTTP endpoints, then remove their own resources. They also compare the original database row counts and checksums before/after. The account used for testing needs create/drop database permissions; the supplied local Developer setup uses `sa`.

The test runner uses `CONTAINER_ENGINE=podman` by default. For Docker, set `CONTAINER_ENGINE=docker` in `.env` or the shell. CI uses Docker.

## Main endpoints

| Method | Route | Behavior |
|---|---|---|
| GET | `/api/applicants/{id}/application-count` | Applicant details and cached application count |
| GET | `/api/applicants/{id}/options` | Available jobs and skills not already associated |
| POST | `/api/applicants/{id}/applications` | Apply and add a skill atomically; invalidate after commit |
| POST | `/api/applicants/{id}/cache` | Clear this applicant's cached count |
| GET | `/api/metrics` | Cache and SQL count-query counters |
| GET | `/health` | SQL readiness and Redis availability |

POST requests require a random per-process bearer token. The browser page supplies it automatically. Requests from cross-site browser origins are rejected. This is a loopback-only local lab, not a public user-authentication system.

```bash
curl -i http://127.0.0.1:3102/api/applicants/1/application-count
```

## Configuration

Copy/generate `.env` from `.env.example`. Shell variables take precedence when Node loads the file.

| Variable | Default | Meaning |
|---|---|---|
| `DB_PASSWORD` | required | Local SQL credential; generated by init-env.sh |
| `DB_HOST` | `127.0.0.1` | SQL Server address |
| `DB_PORT` | `1434` | Host SQL port / Compose published port |
| `DB_NAME` | `RecruitmentDb` | Database; setup fixture requires this name |
| `DB_USER` | `sa` | Local SQL login |
| `DB_TRUST_CERTIFICATE` | `true` | Accept local self-signed SQL certificate; set false with a trusted certificate |
| `REDIS_PORT` | `6380` | Compose published Redis port |
| `REDIS_URL` | `redis://127.0.0.1:6380` | API Redis connection URL |
| `CACHE_TTL_SECONDS` | `60` | Positive cache expiry in seconds |
| `PORT` | `3102` | API port, bound to 127.0.0.1 |
| `CONTAINER_ENGINE` | `podman` | Engine used to create isolated test Redis |

If a port is occupied, update the relevant values before starting. Keep `REDIS_URL` consistent with `REDIS_PORT`.

## Database and sample data

The bootstrap fixture contains 30 applicants, 6 companies, 12 representatives, 15 jobs, 60 applications, and 150 status events, plus skills, experience, and qualifications. Applicant/employer records are fictional; familiar university names provide realistic examples. The fixture is a clean baseline, not an export of later manual changes in the original lab.

## Cache consistency and scope

Successful application writes invalidate only the affected applicant after SQL commits. Failed transactions leave valid cached values intact. Redis failure triggers SQL fallback; failed invalidations remain dirty until successfully cleared. Per-applicant serialization prevents stale cache fills within one API process. A unique process namespace prevents old entries from being reused after API restart.

Direct SQL/Adminer edits bypass invalidation and become visible after TTL expiry or manual cache clearing. Multiple independent API processes need shared invalidation coordination; this demo is designed for a single process. A Redis restart loses cache data, which is safely rebuilt from SQL.

## Stop and clean up

Stop the foreground API with Ctrl+C. Stop Compose services with `docker compose down` or `podman compose down`; the SQL volume is retained. Redis has no disk persistence. To deliberately delete this clone's SQL data too, use `compose down -v` with your chosen engine.

No `.env`, passwords, API tokens, database backups, node_modules, or unrelated local files are committed.

## Kubernetes and Grafana

See [the local Kubernetes guide](docs/KUBERNETES.md) for the kind deployment, database migration, persistent storage, Prometheus scraping/alerts, and integration with the existing local Grafana dashboard. Kubernetes uses app port 3103 and Prometheus port 9091, keeping the original lab separate.

The maintained `@prometheus-io/client` dependency exposes `/metrics`; `/live` is the process liveness probe, while `/health` remains SQL-aware readiness. Metrics include cache outcomes, HTTP and SQL query latency, process resources, SQL availability, and Redis client readiness. Redis server metrics come from a sidecar exporter.
